# BinC rendering

AIR describes render stages through named module metadata. BinC exposes the first useful part of that contract with `vertex` and `fragment` functions.

---

## Current render syntax

```c
vertex float4 pong_vs(device float4* vertices, vertex_id vid) {
    return vertices[vid];
}

fragment float4 pong_fs(float4 position) {
    return float4(1.0f, 1.0f, 1.0f, 1.0f);
}
```

The compiler emits:

- `!air.vertex` metadata for vertex functions
- `!air.fragment` metadata for fragment functions
- `air.vertex_id` for `vertex_id`
- `air.position` for the vertex `float4` output
- `air.position` fragment input metadata for a float4 position parameter
- `air.render_target` index 0 for the fragment float4 return value

The current stage contract is position-first. It is intentionally smaller than a complete general-purpose shader interface.

---

## Pong render pipeline

Pong uses a shared device vertex buffer generated by its BinC compute kernel:

```text
BinC update kernel
    ├─ game physics
    ├─ 3-D arena/grid/HUD geometry
    ├─ motion ribbons
    └─ particles
             │
             ▼
      device float4 vertices
             │
             ├─ BinC vertex stage: pong_vs
             └─ BinC fragment stage: pong_fs
                       │
                       ▼
                CAMetalLayer drawable
```

The host adds a depth attachment and enables alpha blending. The vertex positions use depth layers to separate the background, arena, trails, particles, paddles, and ball.

The fragment stage uses the rasterized position to select the current five-round visual theme:

- rounds 1–4: neon atmosphere
- rounds 5–9: galaxy/star field
- rounds 10–14: green/cyan world
- rounds 15–19: orange/sunset world
- rounds 20–24: ice world
- rounds 25–29: red/void world
- then the theme cycle continues with a continuously changing phase

The game state is passed through the background geometry's depth phase, so the fragment shader remains a BinC shader rather than a host-side color switch.

---

## Motion blur

The ball does not leave permanent history sprites. Each GPU update computes three short ribbons from the ball's current position and velocity:

- long, wide, low-alpha ribbon
- medium ribbon
- short, narrow ribbon

The host enables source-alpha blending. The ribbons are regenerated every frame, tapered, aligned to the direction of travel, and fade into the background. The ball itself remains a sharp foreground shape.

---

## Audio and visual intensity

The host plays a 96-second multi-section soundtrack. At each round transition, it increases playback rate/volume and jumps to a randomized point in the composition. Hit, life-loss, and score events play separate sound effects emitted by the BinC game state.

## Future rendering work

Not currently implemented as general BinC language features:

- arbitrary vertex-output structs
- general `stage_in` records and interpolants
- texture/sampler syntax
- mesh/object shaders
- ray tracing stages

The reference AIR probes document possible future targets but should not be confused with current compiler support.
